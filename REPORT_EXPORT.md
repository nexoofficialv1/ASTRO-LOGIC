# Professional Report Export & Approval Engine

Current export engine: `1.2.0`  
Contract: `professional-report-export-v3`  
Approval engine: `1.0.0`  
Approval statement: `professional-report-approval-statement-v1`  
Source report contract: `professional-consultation-report-v1`

## Purpose

The export layer is a derived-document layer only. It does not calculate or reinterpret astrology. It accepts one saved immutable professional report snapshot, recomputes the source report SHA-256 and refuses generation if stored content, source manifest or report-engine identity no longer matches that hash.

An optional practitioner approval is a separate immutable governance record. It binds the saved report id, consultation id, exact report hash, practitioner identity metadata, decision, note and UTC approval instant into an `approvalHash`. A second `signedReportHash` binds the immutable source report hash to that approval hash and approval-statement version.

This workflow is an in-app practitioner electronic sign-off. It is **not** a certificate-backed PKI/cryptographic digital signature and the UI/export disclosure must say so.

## Approval rules

- one approval record per professional report snapshot;
- practitioner name and designation are mandatory;
- credential/registration reference is optional and is never invented by the app;
- decision is `approvedForClientDelivery` or `approvedWithReservations`;
- `approvedWithReservations` requires a non-empty approval note;
- explicit human acknowledgement is required in the UI before creating approval;
- report id, consultation id and report hash are checked both in application code and SQLite insert guards;
- report snapshots and approvals both reject UPDATE and DELETE;
- changing professional opinion requires a new report snapshot rather than mutating or re-signing the old one.

## Output

- Unsigned PDF/DOCX keeps `astro_logic_report_c<consultationId>_<reportHashPrefix>_<en|bn>.<pdf|docx>`.
- Approved PDF/DOCX uses `astro_logic_report_c<consultationId>_<signedReportHashPrefix>_<en|bn>_signed.<pdf|docx>`.
- Export SHA-256 is calculated from generated bytes and surfaced after generation.
- Approved exports visibly include practitioner name/designation, optional credential, decision, UTC approval time, approval contract, approval hash, signed-report hash, verification QR and the electronic-sign-off disclosure.
- DOCX core properties include source/approval/signed verification metadata and signed DOCX embeds a local PNG verification QR; PDF metadata includes report/signed hash keywords and signed PDF renders the same verification payload as a QR.
- Default folder: app documents `ASTRO_LOGIC/exports`.
- Sharing: platform share sheet through `share_plus`.

## Offline font policy

ASTRO LOGIC does not bundle a third-party font file for report export. DOCX keeps Unicode text and declares a normal system font preference without embedding the font. PDF tries governed system font locations for a Bengali-capable Unicode font (Android Noto Sans Bengali, Windows Nirmala UI, and common Linux/macOS Noto locations). If selected PDF text contains non-ASCII characters and no compatible system font is available, export stops with an explicit error instead of generating missing-glyph boxes. English-only content can fall back to PDF Helvetica.

## Persistence

SQLite schema v9 adds `professional_report_approvals`. The table has a unique `report_snapshot_id`, report/consultation foreign keys, report hash, practitioner metadata, approval decision/note, versioned approval identity, UTC approval time, approval hash and signed-report hash. Database triggers reject approval UPDATE/DELETE and guard report-hash/consultation linkage. Generated PDF/DOCX files remain filesystem artifacts and do not alter persisted report or approval records.

## Validation gates

- source report SHA-256 verification before export;
- approval SHA-256 and signed-report SHA-256 verification when approval exists;
- wrong report↔approval binding rejection;
- practitioner-metadata tamper rejection;
- deterministic signed and unsigned filenames;
- DOCX OOXML package structure test;
- signed DOCX visible approval/hash/disclosure/QR package test;
- Bengali Unicode DOCX test with no embedded `.ttf`/`.otf` part;
- English PDF generation test;
- export byte SHA-256 test;
- tampered source rejection test.

Runtime Flutter tests still require a machine with Flutter/Dart SDK and resolved package dependencies.


## Signed Report Verification & QR Engine v1

Verification contract: `astro-logic-signed-report-verification-v1`.

The QR payload is compact JSON containing only the verification contract, local report snapshot id, consultation id, source report SHA-256, approval SHA-256, signed-report SHA-256 and approval-statement version. Client names, dates of birth, locations and report narratives are not placed in the QR payload.

Offline verification has four outcomes:

1. **Verified against local immutable record** — matching local report and approval records exist, report content recomputes to the stored report hash, approval metadata recomputes to the stored approval hash, and the signed-report hash recomputes correctly.
2. **Valid payload, no local record** — payload structure and its report+approval hash binding are internally consistent, but this database cannot establish practitioner authenticity.
3. **Mismatch/tamper detected** — a matching local identity exists but report content, approval metadata or signed binding does not recompute/match.
4. **Invalid payload** — unsupported contract, malformed fields or inconsistent signed-report hash.

A QR is therefore a transport for verification metadata, not a certificate-backed signature. Verification never upgrades the in-app practitioner sign-off into PKI identity proof. The implementation is fully offline: PDF uses the existing PDF barcode/QR renderer; DOCX uses the pure-Dart `qr` matrix and ASTRO LOGIC's internal PNG encoder. No web QR endpoint is contacted.
